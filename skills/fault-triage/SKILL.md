# 故障排查通用方法

## 何时使用

**触发词**：时好时坏、偶现、间歇性、丢包、断流、设置里找不到、用量余额查不到。

**适用**：手机或 PC 网络质量问题（两类设备共用同一条主线）；系统设置里找不到官方功能开关，怀疑被 ROM/运营商配置隐藏；云平台网页不显示用量/余额，需只读探测接口对账。

**不适用**：一次性、稳定复现的普通 bug（直接看报错即可）；绕过鉴权、破解付费、刷量、规避风控类诉求（一律不做）。

**前置条件**（环境差异导致的必然失败点）：
- 手机采样依赖 ADB 连通。部分国产机型在 Windows 下首次连不上，卡在驱动链：需"厂商套件三件套"——厂商手机助手驱动 + 接口驱动注册 + 重启设备枚举；排查顺序：USB → 接口 → 驱动 → 手机授权弹窗。
- 资源/字节扫描需本机有 unzip、python 等工具；解包只讲方法论，仅排查自己设备官方功能。
- 平台探测需本机已有客户端合法登录配置；没有凭据就不要做。

## 任务目标

1. 把"偶现"变成"可解释"：找到背后的状态变量（信号、负载、配置位、接口），而非干等复现。
2. 把主观体感转成客观时间戳，与自动化采样日志对齐，一次对齐完成全部归因。
3. 产出可验证的缓解/恢复方案，并明确持久还是临时（重启是否回滚）。
4. 全程尽量只读：拿到官方值之前，绝不写入猜测值。

## 方法主线

四步贯穿手机、PC、系统、云端所有故障：

1. **先抓现场，不等复现**：偶现问题不等于随机噪声，先假设它是某种状态的周期性表现，到现场架设秒级持续采样。"偶现"是最重要的证据——它标记系统边界条件，只在负载波动时露出。
2. **对时**：让使用者照常使用并报出"卡了"的时刻，主观体感即变成客观时间戳，与日志精确对齐——对齐一次，全部归因。
3. **分层逐项排除**：硬件/软件 → 系统/应用 → 网络/本地。每层先静态排查（配置、限速、白名单、流量排行），再动态采样；一次只验证一件事。
4. **对照实验一锤定音**：换卡、换制式、换网络、换端点，一次只改一个变量；修复后照常使用一轮，体感与日志双确认。

## 三个战例

### 战例一：网络时好时坏（手机侧 ADB 采样 + 分层对照）

以"打游戏偶发数百毫秒延迟尖峰"为例，根因在基站侧（晚高峰信噪比临界+制式横跳）：

1. **静态排查（系统/应用层）**：ADB 连通后只读采集：`getprop` 看双卡与默认数据卡，`dumpsys netpolicy` 看限速与后台限制，流量排行排除偷流量。
2. **信号判读（网络层）**：`dumpsys telephony.registry` 取 RSRP/SINR/制式。SINR < 5 属临界态，表现正是间歇断流而非持续卡。
3. **实时对时（最有价值的一步）**：手机侧写 `while` 循环脚本，每秒 ping + 记录制式/信号；使用者照常游戏并报时刻。对齐后，本例丢包与 5G/4G 横跳完全同步——归因完成。
4. **对照实验**：双卡对照（切默认数据卡分别 ping）；制式对照（锁 4G 与 5G 自动各跑一轮看断流）。
5. **锁定与恢复**：临时方案用 `cmd phone set-allowed-network-types-for-users -s <slot> <20位二进制掩码>` 锁制式（掩码规则与回滚行为见"坑与红线"）。掩码不进持久库——只写掩码等于白干；持久方案走官方设置路径（见战例二）或同时改持久键（如 `global.preferred_network_mode0`：10=4G，69=5G 自动）。
6. **PC 侧同一条主线**：静态排查（驱动/网卡/电源管理）→ 持续 ping + 路由采样 → 与使用者对时 → 换网对照（有线/热点/不同频段）。

### 战例二：界面上找不到某官方功能（只读五步挖出隐藏开关）

核心判断：**"界面上没有"不等于"系统里没有"**。厂商一般保留完整代码与文案，只用标志位控制可见性，标志位多半在 settings 三张表或 prop 上。全程只读：

1. **扫 prop 找总闸**：`adb shell getprop | grep -iE "<功能词>|msc\."`（部分国产机型用 `msc.*` 前缀 prop 控制可见性）。
2. **拉出系统设置 APK**：`adb pull /system/priv-app/Settings/Settings.apk` 到本机临时目录。
3. **扫资源表找中文文案**：`resources.arsc` 未压缩存 UTF-8，可按字节正则直接搜中文，定位标题与摘要原文。
4. **扫 dex 找键名**：`classes*.dex` 是压缩存储，必须先解压再搜键名/类名/广播名。
5. **定位藏身处**：解压所有 `res/xml/*.xml` 逐个搜键名——命中 `development_prefs.xml` 即"这一项藏在开发者选项"。
6. **反查官方持久键（最值钱的一步）**：让用户在官方 UI 点一次开关，再 `settings get/list` 反查官方把值写进哪个命名空间、什么值——拿到官方持久键，方案才可持久、可恢复。

坑：prop 多受 SELinux 保护，`setprop` 直接 Failed——走设置库或开发者选项；三张表查不到不等于没有（键可能还没被写过）；拿到官方值之前保持只读，绝不写"猜的值"（可能被重启读到成隐患）。

### 战例三：平台用量/余额查不到（只读探针法）

核心意识：**"网页不显示"不等于"查不到"**——账单数据一定有内部接口。

1. **读本机已有配置拿凭据**：从本机已装客户端的配置文件读 provider 的 baseUrl 与 apiKey，现读现用、永不落盘：运行时读入内存，输出只显示"长度+前4位****"。
2. **GET 探测常见端点**：对 `/usage` `/models` `/limits` `/plan` `/credits` `/balance` 等逐个只读 GET，200 即命中；主流平台多有固定余额端点（形如 `GET /user/balance`）。
3. **百分比换算真实花费**：响应只给百分比时，按"百分比 × 官方文档的档位/月度上限"换算真实花费。
4. **以 API 计费侧为准交叉验证**：网页账单可能因部分路径漏记而偏低，对不上时以计费侧为准。

定位边界：仅审计对账，只读 GET，不注入、不绕鉴权、不做平台对抗。

## 坑与红线

**红线（违反即停）**：
- 凭据只在本机内存现读现用，不落盘、不进对话、不进日志。
- 只读优先：拿到官方值之前不写任何猜测值；必须写系统状态时，先说明持久还是临时。
- 热点共享网络下慎做切卡/断网类实验——电脑网络就是手机热点时，切数据卡、开关制式会把观测链路自己切断；实验前先想清楚"会不会把观测者关掉"。
- 不做平台对抗、刷量、规避风控、登录注入。

**高频坑**：
- IPv6-only 通道上 ping IPv4 约半数丢包是探测假象，真实流量正常；精测用 ping6。
- `cmd phone` 掩码只认 20 位二进制串；卡停用态写入会被重置；掩码重启即回滚。
- prop 受 SELinux 保护改不了；dex 要先解压，`resources.arsc` 未压缩可直接扫字节。
- 部分国产机型驱动要"三件套"，首次连 ADB 失败先查驱动链。
- 对照实验一次只改一个变量，否则结论不成立。

## 验证方式

- **间歇性故障**：修复后让使用者照常使用一轮（如打一局），体感与采样日志双确认；断流点与体感时刻的重合消失即为通过。
- **隐藏功能**：开关经官方 UI 生效，`settings get` 能反查出持久键，重启后状态保持。
- **用量探针**：探测结果与网页账单、官方文档上限三方交叉一致。
- 任何"已修复"结论必须有对照实验或双确认证据，不接受"看起来好了"。
