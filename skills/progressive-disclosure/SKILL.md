# 复杂产品说明分层法（渐进披露）

## 何时使用

- 触发词："这个产品说明太复杂""用户根本看不懂""第一屏应该放什么""说明文档/披露方案怎么分层"。
- 适用：任何底层机制复杂、但用户只需要做有限决定的产品：金融产品、技术产品（API、定价、隐私条款）、医疗健康建议、订阅服务等。
- 不适用：面向专业用户的完整技术手册（他们要的就是第三层）；法规要求一次性全文披露的场景（分层只能做导航，不能替代合规全文）。
- 前置条件：能明确写出"用户在这一层要做什么决定"；说不清决定是什么，先别设计层。

## 任务目标

让用户以最短路径拿到"做决定所需且仅需"的信息，同时保证想深究的人随时可下钻到公式与技术证据。核心原则：复杂模型留在后台做计算和约束，前台按需披露。

## 操作步骤

1. **先列决定清单**：写下用户在该场景要做的全部决定（买/不买、用/不用、同意/拒绝），每个决定标注它依赖的最小信息集。
2. **第一层——决定层**：只放能直接支撑决定的信息：要支付什么、获得什么权利、享受价值的前提条件、最大损失/最坏后果。一屏内讲完，用"人话"，不放公式。
3. **第二层——关系层**：用户想多了解时展开：收益与风险的对应关系、关键假设（这些数字在什么条件下成立）、主要变量清单。可以有简单换算，但仍是叙述与表格，不是推导。
4. **第三层——技术层**：完整公式、参数定义、证据与计算过程（如衍生品希腊字母、统计模型、实验数据）。供主动下钻，不要求普通用户阅读。
5. **复杂模型后台化**：模型本身不进文档。它的职责是：(a) 在后台生成第一、二层的数字与约束；(b) 以交互计算器等形式让用户输入自己的参数得到个性化结果；(c) 作为第三层附录可审计。
6. **三层自查**：删掉第一层任何一句，用户会因此做出错误决定吗？会——必须保留；不会——下沉到第二层。第二层同理向第三层下沉。
7. **多入口一致**：每层都要能独立成立（用户直接跳进第三层也能读懂），层间用显式链接，不强制顺序阅读。

## 示例

- 金融产品（原型场景）：第一层 = 费率、保本与否、最大亏损；第二层 = 收益怎么来的、依赖哪些市场假设；第三层 = Delta/Gamma/定价模型与历史回测。
- 技术产品文档：第一层 = 能解决什么问题、免费额度与付费门槛、数据去向与删除权利；第二层 = 性能与成本如何随用量变化、关键限制条件；第三层 = 架构、基准测试方法与完整 API 行为。
- 医疗健康建议：第一层 = 要付出什么（费用/时间/副作用）、最大风险、什么情况必须就医；第二层 = 效果与风险的量级关系、结论依赖哪些研究假设；第三层 = 原始研究、统计口径与排除标准。

## 坑与红线

- **分层 ≠ 隐瞒**：第一层必须包含"最大损失/最坏后果"；把坏消息藏进第三层等于误导。
- **不是按内容多少切**：分层按"决定依赖"切，不按篇幅切；把无关细节塞进第二层会重新制造复杂度。
- 第一层一旦出现公式或术语链条，说明决定清单没列对，回到第 1 步。
- **各层数字必须同源**：全部来自同一个后台模型，禁止第一层一个口径、第三层另一个口径。
- 合规场景（金融、医疗等）中，分层呈现不豁免完整披露义务；该给的全文仍要留有入口。

## 验证方式

- 决定测试：请 3~5 名未接触过产品的用户只看第一层，能正确复述"要付什么、得到什么、最坏怎样"，且方向性决定彼此一致。
- 下钻测试：从第三层任意一节直接进入，不读前两层也能理解该节。
- 一致性抽查：第一、二层的每个数字都能在第三层/后台模型中找到出处，口径零冲突。
