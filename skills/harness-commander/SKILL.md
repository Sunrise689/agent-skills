# 复杂任务指挥框架 V3（Harness Commander）

**核心理念**：让 Agent 完成一个有边界、可恢复、可沉淀的闭环。V2 Pro 强调——不是照单执行，而是在全局视角下找最短可靠路径，用最小动作达成目标。

**简单任务直接跳过**。1-2 步问答、纯信息检索、无副作用操作，不套用任何流程。框架本身有成本。

## 一、触发判断门（Gate）

### ✅ 视为复杂任务，启动框架

以下条件满足任意一条：

- 任务含 **≥3 个独立环节**（搜索→修改→验证→交付→沉淀），环节间存在依赖链
- 需调度 **≥2 个子 Agent** 并行工作后汇总对账
- 含**不可逆操作**：生产部署、数据库变更、文件批量删除/覆盖、Git push、对外发送
- 验收边界模糊，需先对齐"什么是完成"再推进
- 全局审视发现**任务表述可被大幅优化**（见第三章）——用户说的是需求，不是最优路径

### ❌ 跳过框架

- 单轮问答、解释说明、代码阅读、信息查询
- ≤2 步即可闭环的轻量任务
- 无副作用的纯分析请求

> **判断铁律**：有疑惑按复杂任务处理。宁可多拆一步，不可让不可逆动作裸奔。

## 二、需求引导模式（User Elicitation）⭐V3 新增

**核心理念**：信息不足时不瞎猜——自动判断需求完整度，信息充足直接跳过，信息不足才触发引导一次性问清关键问题。

### 2.1 触发门（Elicitation Gate）

**自动跳过引导（直接进入全局优化+七步闭环）：**
- 目标/对象/产出 ≥3 个关键要素齐全
- 需求描述足够详细（通常 ≥30 字且有具体信息）
- 用户主动给出验收标准或约束

**自动触发引导：**
- 需求过短或模糊（如"帮我做个东西""优化一下"）
- 关键要素缺失（没有目标/对象/产出中任一）
- 有多个合理解释，无法确定用户真实意图
- 用户明确说"不知道怎么做/你先问我"

### 2.2 引导方式

**一次问 3-5 个关键问题，集中在一次输出里。** 不是一个一个问（效率太低），也不是问 10 个（用户答不完）。

**A/B 分类**：能基于行业通识合理推断的自己补全并标注"自动补全请确认"（A 类）；猜错会导致真实业务错误的才问用户（B 类）。

**五维提问**（从核心到外围）：目标（做什么）→对象（给谁用/作用于什么）→产出（交付什么）→约束（限制/不能做什么）→验收（怎样算完成）。只问缺失维度，每个维度最多 1 问。

**第二轮追问**：第一轮回答后仍有关键缺口→最多再问 2-3 个。连续两轮没有新增有效信息→停止追问，基于已有信息开工并标注所有假设。

### 2.3 引导后确认

用户回答后：
1. **复述**：用 3-5 句话重述理解的任务
2. **假设**：主动列出关键假设，让用户说"对/不对"
3. **简报**：确认后按 task-brief 模板输出结构化任务简报，进入七步闭环

### 2.4 与各模块衔接

- **触发判断门（Gate）**先于 Elicitation Gate（先判断是否复杂→再判断需求是否清晰）
- 引导产物（复述+假设+任务简报）直接作为 Step 1 理解的输入
- 引导过程受**循环收敛控制**约束（最多 2 轮追问，防问个没完）
- 引导的提问受**误报防火墙**约束（A 类能自己补的不许拿去问用户）

> 详细逻辑见 `references/user-elicitation.md`。

## 三、全局优化审视（执行前必做）⭐V2 Pro 核心

接到复杂任务后，不立刻拆解。先用全局视角审视——用户说"我要 A→B→C→D"，不等于你一定要按 A→B→C→D 执行。两个程序结果相同，一个 50 行一个 5 行，选 5 行。任务同理。

### 四问

| 问题 | 说明 |
|---|---|
| **能否并行？** | A 和 B 无依赖→并行执行；B 只读不写→可与 A 并行 |
| **能否合并？** | B 的结果可被 C 一步产出→合并；两轮对话可一轮完成→合并 |
| **能否省掉？** | 某步骤的产出不是最终交付必须的→跳过；纯"锦上添花"步骤→跳过 |
| **能否嵌入？** | 验证可嵌入执行而非单开一步→嵌入；交付可边做边交而非单开一步→嵌入 |

### 拆解互斥原则（MECE）

拆解点必须**独立不重叠**。金融 vs 股市是包含关系，需先拆边界再切入。子任务之间不应有隐含的交叉依赖导致信息重复采集或冲突裁决。

### 护栏

优化路径≠偏离用户真实目标。合并步骤不改变最终交付的内容和验收标准。优化后必须输出**对比**：原方案步骤数 vs 优化后步骤数，省掉了几步、为什么。

> 详细逻辑见 `references/global-optimization.md`。

## 四、七步闭环

每步产出**可见中间物**（文件/结构化输出）。禁止"大脑中的步骤"。

| 步骤 | 产出物 | 说明 |
|---|---|---|
| **1. 理解** | 目标一句话 + 验收边界 + 残余风险声明 + 状态总账初始化 | 和用户对齐后再推进，不推测目标；初始化 `HARNESS_STATE.json` |
| **2. 范围** | 文件清单 + 依赖图 + 风险点 + 爆炸半径 | 穷举工具搜索，不凭记忆；标注 blast radius 风险 |
| **3. 执行** | 子 Agent 调度 + 各子任务独立证据 + Worker 监控 | 用固定简报模板派活；启动心跳监控；写入状态总账 |
| **4. 验证** | 每子任务验证结果 + Evidence State 等级 | 自动化验证优先；检查点记录已通过的验证 |
| **5. 故障** | 根因 + 修复方案 + 重跑验证 + 分类归档 | 按四分类归档失败；走升级链；写入状态总账 |
| **6. 交付** | 交付物 + 收尾自检通过 | 见第十二部分自检清单 |
| **7. 沉淀** | Loop Spec Card / Skill / 规则 / 脚本 | 同类任务出现≥2次则必须沉淀 |

## 五、调度原则

### 5.1 固定任务简报（Task Brief）

派活必须用固定简报格式。口头布置容易漏约束、漏验收、漏上下文。详见 `references/task-brief.md`。

### 5.2 证据/判断分离

- **确定性工作**（搜索、编译、测试、统计）由脚本/工具执行，产出结构化 evidence bundle
- **LLM 只对结构化证据做定性判断**，不允许凭"感觉"跳过工具验证
- 不让 LLM 手算评分、手写格式化报告

### 5.3 子任务信息隔离

- 并行子 Agent 之间**不共享结论**，各自独立采集
- 子 Agent 只收自己通道的原始证据，不接受其他通道的结论
- 主指挥（Master）独占定级/定 severity 权
- 子 Agent 禁止再委托，禁止写文件（只读分析）

### 5.4 只读 + 显式授权

- 方案阶段全程只读
- 不可逆操作须**单独确认**：创建文件/变更/清理/定时任务/外部写入——每项需显式授权
- Owner 或关键值未解析时，停止并写出恢复条件；禁止编造

### 5.5 分层模型分配（Tier 分配）⭐V2 Pro 新增

按任务复杂度分配模型能力，**省钱且精准**：

| Tier | 模型档位 | 适用任务 |
|---|---|---|
| **0** | 极简/嵌入式模型 | 纯搜索、文件读取、格式转换、批量文本处理 |
| **1** | 标准模型 | 代码理解、简单修改、脚本编写、单元测试 |
| **2** | 强模型 | 多文件架构决策、跨模块重构、复杂调试 |
| **3** | 最强模型 | 全局审视、方案设计、对账裁决、安全审查、沉淀复盘 |

主指挥用 Tier 3；子 Agent 按任务类型分配 Tier 0-2。禁止让 Tier 3 模型做文件读取。

## 六、安全护栏（Guardrails）⭐V2 Pro 新增

三道护栏，任何一道触发即拦截。

| 护栏 | 规则 | 违反时处理 |
|---|---|---|
| **黑名单** | `rm -rf`/强 push/删库/批量覆盖/对外发送 → 必须人工确认 | 停止执行，输出"需人工确认：{操作}" |
| **范围检查** | 只做用户要求的。用户说改 A，顺手改 B → 拦截 | 停止，向用户报告越界操作并等待确认 |
| **歧义拒绝** | 指令不清先问不猜。可有两种以上合理解读的指令 → 拦截 | 列出可能的含义，要求用户明确选择 |

> 详细规则与示例见 `references/guardrails.md`。

## 七、循环收敛控制 ⭐V2 Pro 新增

重复执行同一环节时自动触发。

### 循环预算

默认**最多 3 轮**。超过即视为死循环/低效循环，强制停止并升级用户。

### 收敛检查（每轮结束执行）

问自己：

1. 这轮比上轮**实质前进了多少**？（不是"我改了一行"而是"离目标近了 X%"）
2. 同样的错误是否**再次出现**？（是→立即停止，不是继续尝试）
3. 是否在**同一位置打转**？（是→死循环，立即停止）

有实质进展才允许下一轮。3 轮无进展→升级用户。

### 循环质量分级

| 分级 | 轮次 | 判定 |
|---|---|---|
| **高效收敛** | 1-2 轮达成目标 | 理想状态 |
| **缓慢收敛** | 3 轮，每轮有实质进展 | 可接受，完成后需沉淀为 Loop |
| **死循环** | 同一位置打转或同样错误重复 | 立即停止，升级用户 |

> 核心哲学：10 人+合理流水线 > 100 人+混乱加班。一轮到位 > 十轮空转。
> 详细逻辑见 `references/loop-control.md`。

## 八、失败分类 + 升级链 ⭐V2 Pro 新增

失败不只说"失败了"，要分类+走升级链。

### 四分类

| 类别 | 判断标准 | 处理方式 |
|---|---|---|
| **输入问题** | 输入本身有误（路径不存在、语法错误、格式不兼容） | 报告具体输入错误，等待用户修正 |
| **逻辑问题** | 方案本身有 bug（选了不可行的算法、依赖链断裂） | 调整方案，重试 ≤2 次；仍失败→升级用户 |
| **环境问题** | 环境缺席（依赖未安装、权限不足、网络不通） | 先怀疑环境结构不足而非模型能力不足；报告缺失项 |
| **模型问题** | LLM 理解错误/幻觉/上下文丢失 | 换模型档位重跑，2 次仍失败→升级用户 |

### 升级链

```
失败 → 分类 → 调整方案 → 重试（≤2次）
   │
   └→ 仍失败 → 升级用户（带失败摘要 + 已尝试方案 + 建议）
```

> 关键原则：进展慢优先怀疑"环境结构不足"而非"模型能力不足"。详见 `references/recovery.md`。

## 九、证据状态四档

**第一铁律：配置了 ≠ 使用了。**

| 等级 | 含义 | 得分上限 |
|---|---|---|
| **Present (74)** | 配置/文件存在于系统中 | 74 |
| **Wired (84)** | 配置已连接到执行路径 | 84 |
| **Exercised (94)** | 在真实或模拟环境运行过 | 94 |
| **Outcome (100)** | 运行结果直接支撑结论 | 100 |
| **Missing** | 无任何可观察证据 | **59（封顶）** |

> 详见 `references/evidence-states.md`。

## 十、误报防火墙

三条穿透检查——触发任意一条即返回"证据不足"：

| # | 检查 | 说明 |
|---|---|---|
| 1 | **次数多 ≠ 需求** | `deploy` 出现 100 次不代表存在统一部署流程 |
| 2 | **关键词相同 ≠ 同一工作流** | 按目标+输入形状+验收边界聚类，非按关键词 |
| 3 | **配置存在 ≠ 被使用** | import 不说明调用链已连通 |

任务完成（第七步沉淀）时，判断该不该固化为 Loop。

## 十二、收尾自检清单

交付前逐项勾过：

- [ ] **闭环** — 验收边界内所有项已完成，残余风险已声明
- [ ] **可复现** — 他人不依赖本次对话上下文也能复现
- [ ] **证据支撑** — 每条结论证据 ≥ Wired (84)；低于 84 的标注置信度不足
- [ ] **已对账** — 多源证据已对账降噪，合并了同目标+同后果+同修复路径的候选项
- [ ] **该沉淀** — 同类任务出现 ≥2 次→已沉淀为 Loop Spec Card/Skill/规则/脚本
- [ ] **残余风险声明** — 未验证项、未知依赖、爆炸半径外的不确定区域已列明
- [ ] **全局优化自检（V2 Pro）** — 执行前做了四问审视？执行路径是否最短？有无无效步骤？
