# 需求引导模式（User Elicitation）

**核心哲学**：Harness 有两个方向——管住 AI（已有）和管住人（本次新增）。有些用户一句话甩过来"帮我做个东西"，信息严重不足。如果直接干活就会瞎猜、跑偏、返工。需求引导模式 = 自动判断信息完整度，信息充足直接跳过，信息不足才一次性问清关键问题。

## 一、触发门（Elicitation Gate）

接任务后先评估用户需求的信息完整度。**不是所有人都问**——信息充足的直接跳过。

### 跳过条件（自动跳过引导，直接进入全局优化+七步闭环）

满足任意一条即跳过：

| 条件 | 判据 |
|---|---|
| 关键要素齐全 | 目标（做什么）/对象（给谁用/作用于什么）/产出（交付什么）≥3 个要素齐全 |
| 描述足够详细 | 需求描述通常 ≥30 字且包含具体信息（路径、文件名、技术栈、验收标准等） |
| 用户给出验收标准或约束 | 用户主动说了"要求 XX""必须 XX""不能 XX""验收标准是 XX" |
| 用户明确表示无需引导 | "直接做""开始吧""不需要问了" |

### 触发条件（自动触发引导）

满足任意一条即触发：

| 条件 | 判据 |
|---|---|
| 需求过短或模糊 | "帮我做个东西""优化一下""修一下 bug"——没有具体对象和产出 |
| 关键要素缺失 | 没有目标/对象/产出中任一要素 |
| 多解歧义 | 同一句话有两种以上合理解释，上下文无法区分用户真实意图 |
| 用户主动请求引导 | "不知道怎么做""你先问我""你说说看需要什么信息" |

### 判定示例

| 用户输入 | 判定 | 理由 |
|---|---|---|
| "在 auth 模块加 JWT 认证，支持 refresh token，登录失败 3 次锁定 15 分钟" | **跳过** | 目标+对象+产出+约束齐全，≥30 字，信息充足 |
| "帮我写个脚本" | **触发** | 没说什么脚本，没说什么用途，缺目标+对象+产出 |
| "优化首页加载速度，目标 FCP < 1.5s" | **跳过** | 有目标（FCP < 1.5s）+对象（首页）+验收标准，信息充足 |
| "这个代码不太好，改一下" | **触发** | 没说什么不好，没改什么文件，没验收标准 |

## 二、A/B 分类原则

不是所有信息缺口都要问用户。先分类：

### A 类：自动补全（不问你）

能基于行业通识、典型场景合理推断的信息缺口——**自己补全并标注，等用户确认**。

| 缺口类型 | 自动补全示例 | 标注方式 |
|---|---|---|
| 技术栈 | 上下文是 React 项目、没提语言→自动补"用 TypeScript" | "我假设使用 TypeScript，请确认" |
| 通用最佳实践 | "做登录"没提加密→自动补"密码用 bcrypt 加密存储" | "自动补全：密码用 bcrypt，请确认" |
| 合理默认值 | "分页查询"没提每页条数→自动补"默认每页 20 条" | "自动补全：默认每页 20 条，请确认" |
| 行业约定 | "REST API"没提格式→自动补"JSON 格式、标准 HTTP 状态码" | "自动补全：JSON + 标准状态码，请确认" |

**A 类判断铁律**：补错了后果可控（用户可以一句话修正）→ A 类。补对了省一轮追问，补错了用户纠正就行。

### B 类：提请用户（必须问）

猜错会导致真实业务错误、方向跑偏、需推倒重来的——**必须问用户**。

| 缺口类型 | 为什么必须问 | 示例 |
|---|---|---|
| 目标本质 | 猜错目标全盘皆错 | "优化"是性能优化还是架构重构？两方向完全不同 |
| 用户对象 | 不同用户需要完全不同的方案 | "做个管理后台"——是给运营用还是给开发用？权限模型不同 |
| 业务规则 | 业务规则没有"通识" | "订单超时取消"——超时是 15 分还是 30 分？这只有用户知道 |
| 交付形式 | 交付形式决定全部工作流 | 产出是可运行代码？设计文档？分析报告？工作内容完全不同 |
| 不可逆约束 | 踩了约束线无法回滚 | "不能碰数据库""必须在现有框架内""不能引入新依赖" |

**B 类判断铁律**：补错会导致 ≥30% 的工作推倒重来→ B 类。宁可多问一句，不可重做半天。

## 三、五维提问框架（3-5 问模板）

一次问 3-5 个关键问题，集中在一次输出里。按五维从核心到外围，跳过已有信息的维度。

### 维度 1：目标（做什么、解决什么问题）

这是最核心的维度——目标不清楚，后面的问题没有意义。

**当目标缺失时，示例提问：**
- "你希望通过这个功能/工具解决什么具体问题？"
- "这个任务的核心目标是什么？比如提升性能/增强安全/改善体验/实现新功能？"
- "做完后最关键的改变是什么？"

### 维度 2：对象（给谁用、作用于什么）

**当对象缺失时，示例提问：**
- "这个产出是给谁用的？终端用户/开发者/运维/内部团队？"
- "作用于哪个系统/模块/文件？可以给我文件路径或模块名吗？"
- "是在现有项目基础上改，还是从零新建？"

### 维度 3：产出（交付什么）

**当产出缺失时，示例提问：**
- "你期望的最终交付物是什么？可运行代码/设计文档/分析报告/配置方案？"
- "交付物有没有格式或语言要求？"
- "有没有可以参考的类似产出？"

### 维度 4：约束（有什么限制、不能做什么）

**当约束缺失但可能重要时，示例提问：**
- "有没有技术栈限制？必须用的/不能用的语言/框架/库？"
- "有没有时间或资源约束？"
- "有没有绝对不能碰的部分？比如不能改数据库、不能改公开 API？"

### 维度 5：验收（怎样算完成）

**当验收缺失时，示例提问：**
- "你怎么判断这个任务做完了？有没有具体的成功标准？"
- "有没有必须跑通的测试或用例？"
- "如果没有明确验收条件，我完成时会列出 3-5 条建议验收标准供你确认，可以吗？"

### 3-5 问组装规则

1. **只问缺失的维度**：用户已经说了目标，就不问目标
2. **优先问核心维度**：目标 > 对象 > 产出 > 约束 > 验收
3. **每个维度最多 1 个问题**：一个维度拆成 2 个问题是浪费
4. **总问数 3-5 个**：如果只有 2 个维度缺失，问 2-3 个（可以加具体追问）；如果 5 个都缺，选最核心的 4-5 个
5. **问题要具体可回答**：不问你"说说你的需求"，问你"给谁用、解决什么问题"

### 引导输出格式示例

```
这个需求还需要几个关键信息才能准确执行，我一次问完：

1. 【目标】这个工具/功能要解决什么具体问题？
2. 【对象】给谁用的？终端用户还是开发者？
3. 【产出】期望的交付物是什么？代码/文档/配置？
4. 【约束】有没有技术栈限制或不能碰的部分？

另外，以下信息我根据常见实践自动补全了，请确认：
- 我假设使用项目现有的技术栈（不引入新框架）
- 我假设需要包含基本的错误处理和日志
```

## 四、复述 + 假设确认

用户回答引导问题后，不是直接开工——先复述并确认理解正确。

### 4.1 复述模板

用 3-5 句话重述你理解的任务：

```
根据你的回答，我理解的任务是：

【目标】{一句话说清要达成什么}
【对象】{给谁用/作用于什么}
【产出】{交付什么}
【约束】{关键限制条件}
【验收】{怎样算完成/验收标准}

以上理解对吗？
```

### 4.2 假设列表

列出你主动做的关键假设（包括 A 类自动补全和未问到的合理推断）：

```
此外，我的关键假设是：
1. 我假设 {假设内容} — 对吗？
2. 我假设 {假设内容} — 对吗？
```

用户只需逐条回答"对"或"不对"。假设列表不超过 5 条。

### 4.3 确认后输出任务简报

用户确认后，按 `references/task-brief.md` 模板输出结构化任务简报，然后进入七步闭环 Step 1 理解。

## 五、防过度追问规则

需求引导受循环收敛控制约束——不能无限追问。

### 预算

| 预算项 | 上限 |
|---|---|
| 引导总轮次 | **最多 2 轮**（首轮 3-5 问 + 第 2 轮 2-3 问） |
| 第二轮触发条件 | 第一轮回答后仍有关键要素缺失（目标/对象/产出任一） |
| 停止条件 | 连续两轮没有新增有效信息（用户重复"就是优化一下"之类） |

### 超预算处理

两轮追问耗尽后，**不再追问**。处理方式：
1. 基于已有信息开工
2. 在任务简报的残余风险声明中列出"因信息不足未确认的假设"
3. 执行中遇到假设不成立的情况→立即暂停并升级用户

### 不与其它拦截混淆

- 需求引导的追问 ≠ 执行中的循环（Loop Control 管后者）
- 需求引导的提问 ≠ 歧义拒绝（Guardrails 的歧义拒绝管执行中的指令歧义）
- 引导两轮耗尽后的"标注假设开工"≠ 瞎猜——是基于已有信息的最合理推断

## 六、与各模块的衔接

### 6.1 在总体流程中的位置

```
用户提需求
    │
    ▼
触发判断门（Gate）── 不复杂 → 直接处理，不套框架
    │ 复杂
    ▼
需求引导门（Elicitation Gate）── 信息充足 → 跳过引导
    │ 信息不足
    ▼
引导（1-2 轮）
    │
    ▼
复述 + 假设确认
    │
    ▼
全局优化审视（Global Optimization）
    │
    ▼
七步闭环执行
```

### 6.2 与触发判断门（Gate）的关系

- Gate 在前：先判断任务是否复杂到需要框架
- Elicitation Gate 在后：确认需要框架后，再判断需求是否清晰
- 如果 Gate 判定不复杂，不进入 Elicitation Gate（简单任务直接处理）

### 6.3 与七步闭环的关系

- 引导产物（复述+假设+任务简报）直接作为 Step 1 理解的输入
- 复述内容 = Step 1 的"目标一句话"
- 假设列表 = Step 1 的"残余风险声明"的初始输入
- 用户确认后的任务简报 = Step 2 范围扫描的上下文

### 6.4 与循环收敛控制的联动

| 场景 | 走哪个流程 |
|---|---|
| 用户回答引导问题后，需要追问第二轮的 | 走本文件第 2 轮追问规则 |
| 引导两轮耗尽，决定"标注假设开工" | 走本文件超预算处理 |
| 引导已完成，执行中同一步骤重复失败 | 走 `loop-control.md` 收敛检查 |
| 用户对引导复述说"不对，重新理解" | 重置引导预算为 2，重新引导（不算执行循环） |

### 6.5 与误报防火墙的联动

误报防火墙的三条穿透检查同样约束需求引导的提问：
- **次数多 ≠ 需求**：不能因为"做过很多类似项目"就跳过引导
- **关键词相同 ≠ 同一工作流**：不能因为"这个关键词常见"就假设用户意图
- **配置存在 ≠ 被使用**：不能因为"项目用 React"就假设用户要 React 方案

同时，A/B 分类原则（本章第二节）直接约束引导提问——必须先用 A/B 分类过滤后再提问，不可把可自动补全的 A 类信息当作 B 类去问用户。

### 6.6 与安全护栏的联动

| 护栏规则 | 在引导中的体现 |
|---|---|
| 歧义拒绝 | 引导阶段就已经处理了需求层面的歧义，执行中歧义由 Guardrails 的歧义拒绝独立拦截 |
| 范围检查 | 引导阶段确定的产出和约束 = 后续范围检查的基准线 |

## 七、反模式（不要这样做）

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 信息充足还追问 | 浪费用户时间，显得啰嗦 | 先过 Elicitation Gate，跳过条件满足直接跳过 |
| 一次只问 1 个问题 | 效率极低，问完 5 轮用户早跑了 | 一次问 3-5 个，集中输出 |
| 问 10 个问题 | 用户答不完，大部分问题其实 A 类可自动补 | 先用 A/B 分类过滤，只问 B 类 |
| 问开放式问题 | "说说你的需求"= 用户不知道怎么答 | 问具体维度的具体问题 |
| 超过 2 轮还在问 | 追问到第 3 轮说明不是信息问题而是方向问题 | 2 轮后标注假设直接开工 |
| 不确认就开工 | 用户的"对"可能是没仔细看 | 必须等用户明确确认复述和假设 |
| 把 A 类当 B 类问 | 用户觉得"你该知道的还问我" | A/B 分类后再提问 |

> **一句话原则**：信息够就直接干，信息不够就一次性问清。不问开放式废话，不超 2 轮，确认后开工。
