# 全局优化思维（Global Optimization）

**核心哲学**：用户描述的是需求（Desire），不是最优执行路径（Path）。两个程序结果相同，一个 50 行一个 5 行，选 5 行。任务拆解同理——拿到需求后先全局审视，找最短可靠路径。

## 一、优化四问

执行任何复杂任务前，必须逐问审视用户的任务描述。答案是"是"就调整方案，不是跳过。

### 第一问：能否并行？

**含义**：把串行的两个步骤改成并行执行。

**判定**：
- A 和 B 之间没有依赖关系（B 不需要 A 的输出）→ **可并行**
- B 只读不写（B 搜索代码，A 修改代码）→ B 可提前与 A 并行
- A 和 B 共享同一个文件写入 → 不可并行（有写冲突）

**示例**：
```
原方案：先搜索代码 → 再分析结构 → 再写修改方案
优化后：搜索代码 + 分析结构 并行 → 汇总写修改方案
节省：1 步（分析不必等搜索完成，两者可同步进行）
```

### 第二问：能否合并？

**含义**：把需要多步才能产出的结果，合并成一步产出。

**判定**：
- B 的结果是 A 的子集（A 本来就要产出 B 的内容）→ **可合并**
- A 和 B 面向同一目标物、使用同一工具 → **可合并**
- 合并不改变最终交付质量和验收覆盖 → **可合并**

**示例**：
```
原方案：统计文件数 → 读文件内容 → 分析质量 → 写报告 → 写建议
优化后：读文件内容时顺带统计和质量分析 → 报告+建议合并产出
节省：2 步（统计被嵌入读取、报告和建议在分析过程中自然形成）
```

### 第三问：能否省掉？

**含义**：某步骤的产出不是最终交付必须的——直接跳过。

**判定**：
- 这一步产出的是"锦上添花"（非用户要求的交付物）→ **可省掉**
- 这一步是"为了保险"但实际风险极低 → **可省掉**
- 这一步的结论对后续决策无影响 → **可省掉**
- 这一步是纯格式化/美化工作（不影响功能验收）→ **可省掉**

**示例**：
```
原方案：改代码 → 跑测试 → 生成覆盖率报告 → 写变更日志 → 生成 UML 图 → 交付
优化后：改代码 → 跑测试 → 交付（覆盖率报告、变更日志、UML 图均为锦上添花）
节省：3 步
```

### 第四问：能否嵌入？

**含义**：把独立的步骤嵌入到另一个步骤中并行完成，而不是单独拿出来。

**判定**：
- 验证可在执行阶段顺带完成（不必单开一步）→ **可嵌入**
- 信息搜集可在修改代码时顺带完成 → **可嵌入**
- 沉淀产出可在交付时顺带完成 → **可嵌入**

**示例**：
```
原方案：理解 → 范围 → 搜索 → 修改 → 搜索验证 → 测试 → 交付 → 沉淀
优化后：理解 → 范围 → 修改（含搜索）→ 测试验证 → 交付（含沉淀）
节省：2 步（搜索嵌入修改、沉淀嵌入交付）
```

## 二、拆解互斥原则（MECE）

**MECE = Mutually Exclusive, Collectively Exhaustive（相互独立，完全穷举）**

### 规则

1. **拆解点之间必须独立不重叠**
   - ❌ 子任务 A："检查金融模块" + 子任务 B："检查股市模块"（股市是金融的子集，包含关系）
   - ✅ 子任务 A："检查支付模块" + 子任务 B："检查信贷模块"（互斥）

2. **不准隐含交叉依赖**
   - 子任务不能依赖"另一个子任务顺便做的事"
   - 每个子任务的输入必须来自明确分配的通道

3. **拆解覆盖全部验收范围**
   - 所有子任务合起来刚好覆盖用户要求，不多不少

### 反模式

| 反模式 | 问题 | 修正 |
|---|---|---|
| 按技术栈拆解（前端/后端/数据库） | 不同栈可能修改同一个功能 | 按功能拆解（认证/支付/通知），每个功能可能跨栈但范围独立 |
| 按文件类型拆解 | 修改同一功能可能涉及多类文件 | 按逻辑模块拆解 |
| 按时序拆解（阶段1→2→3） | 当阶段间无真依赖时浪费了并行机会 | 先问"能否并行" |

## 三、系统优化优先

**类比**：代码 reviewer 不会照原代码的结构给优化建议，而是从"这段代码本可以怎么写才最短"出发。任务指挥也一样——用户的"步骤描述"只是输入，不是最优解。

### 优化自检清单（执行前必过）

- [ ] 用户说的步骤中，有无**只读无依赖**的可提前并行？
- [ ] 用户的"A→B→C"中，B 和 C 是否能**合并为一步**？
- [ ] 用户要求的产出物中，有无**非核心交付**可建议跳过？
- [ ] 验证步骤能否**嵌入**执行步骤中（边做边验）而非单开？
- [ ] 拆解出的子任务是否**互斥**（无包含关系、无隐含交叉依赖）？
- [ ] 优化后的方案是否**不偏离**用户真实目标？合并/省略不改变最终交付？

### 输出对比

优化完成后，必须在状态总账或理解阶段输出中记录：

```text
【全局优化对比】
原方案步数: 8（理解→范围→搜索→分析→方案→修改→测试→交付）
优化后步数: 5（理解→范围→搜索+分析并行→修改+方案嵌入→测试+交付）
节省: 3 步
理由: 搜索和分析无依赖可并行；方案可在修改过程中边改边调，无需单开一步
偏离用户目标: 否（最终交付一致）
```

## 四、护栏

优化路径≠偷工减料。以下情况**不适用优化**：

| 情况 | 说明 |
|---|---|
| 用户明确要求按特定顺序执行 | 尊重用户的顺序约束 |
| 合并/嵌入会降低交付质量 | 质量优先于效率 |
| 省掉的步骤是用户明确要求的交付物 | 用户要的报告必须给 |
| 并行会引入竞争条件（写冲突） | 安全优先于并行 |
| 缺乏对合并方案可行性的把握 | 不确定时走稳妥路径 |

> **一句话原则**：用户说的是需求，你说的是方案。需求不能打折扣，方案可以找最短路径。
