# 失败分类 + 升级链（Recovery）

**核心问题**：失败不是终点。每次失败必须分类归档，并按升级链处理，而不是同一套路反复重试。

## 一、失败四分类

失败不只是一个"出错了"。分类决定处理策略。

### 1. 输入问题（Input Failure）

**判断标准**：输入本身有误，不是执行逻辑的问题。

| 现象 | 示例 |
|---|---|
| 用户提供的文件路径不存在 | "打开 `/app/src/auth.ts`" → `ENOENT: no such file` |
| 数据格式与预期不符 | "解析 JSON" → `JSON.parse error`，输入文件是 YAML |
| 参数值在合法范围外 | "删除第 999 条记录" → 数据库只有 10 条 |
| 指令自相矛盾 | "把 A 改成 B 同时保持 A 不变" |

**处理方式**：
1. 不调整方案（方案本身可能是对的）
2. 报告具体输入错误：指出哪个输入、哪个值、为什么不对
3. 等待用户修正输入后重新执行
4. 不重试、不猜测正确输入

### 2. 逻辑问题（Logic Failure）

**判断标准**：方案/策略本身有 bug，修正策略可能解决。

| 现象 | 示例 |
|---|---|
| 算法选择了不可行的路径 | 计划用正则解析 HTML→解析不到期望内容 |
| 依赖链断裂 | 步骤 C 依赖步骤 B 的输出，但 B 没有产出所需字段 |
| 顺序错误 | 先调用了还未创建的 API |
| 假设不成立 | 假设所有文件都是 UTF-8，实际有 GBK 文件 |

**处理方式**：
1. 分析为什么当前方案不可行（写出根因）
2. 调整方案（不是微调参数，是换思路）
3. 重试 **≤2 次**
4. 2 次调整均失败 → 升级用户（带已尝试方案+根因分析）

### 3. 环境问题（Environment Failure）

**判断标准**：执行环境缺少必要条件，不是代码或逻辑问题。

| 现象 | 示例 |
|---|---|
| 依赖未安装 | `command not found: eslint` |
| 权限不足 | `EACCES: permission denied` |
| 网络不通 | `ENOTFOUND`、超时 |
| 磁盘空间不足 | `ENOSPC` |
| 内存不足 | OOM kill |

**处理方式**：
1. 报告缺失的依赖/权限/资源（具体路径/包名）
2. 如果是 Agent 可自行安装的依赖（`npm install` 等**非系统级**）→ 可尝试安装后重试
3. 如果是系统级依赖/权限 → 升级用户，建议安装命令
4. 关键原则：**优先怀疑环境结构不足而非模型能力不足**

### 4. 模型问题（Model Failure）

**判断标准**：LLM 理解错误、幻觉、上下文丢失，不是代码或环境问题。

| 现象 | 示例 |
|---|---|
| 明显理解错误 | 用户说修 A，Agent 一直在修 B |
| 幻觉编造 | 引用不存在的 API/路径/命令 |
| 上下文丢失 | 前面确认过的约束后面忘了，重复确认 |
| 质量塌陷 | 输出越来越短/越来越不相关（上下文窗口满） |

**处理方式**：
1. 换模型档位重跑（通常是升一档）
2. 重试 ≤2 次
3. 2 次均失败 → 升级用户
4. 如果是上下文满导致的，先压缩上下文再重跑

## 二、升级链（Escalation Chain）

```
失败发生
  ↓
分类：输入/逻辑/环境/模型？
  ↓
├── 输入问题 → 报告具体错误 → 等待用户修正 → 不走升级链
  ↓
├── 逻辑/环境/模型问题 → 调整方案 → 重试（≤2次）
  │        ↓
  │   成功 → 继续执行
  │        ↓
  │   仍失败 → 升级用户
  ↓
升级用户格式：
  【失败摘要】
  - 失败步骤: <第 X 步: 名称>
  - 失败分类: <输入/逻辑/环境/模型>
  - 根因: <一句话>
  - 已尝试方案:
    1. <方案1> → <结果>
    2. <方案2> → <结果>
  - 建议: <下一步建议>
```

## 三、关键原则

### 3.1 进展慢先怀疑环境

当执行反复卡在同一位置、每次都是不同的小错误时——**优先怀疑"运行环境的结构不完整"而非"模型不够聪明"**。模型反复犯不同的小错，往往是因为缺少确定性工具（linter/编译器/类型检查）的即时反馈。

### 3.2 重试不等于重做

重试必须在调整方案后进行。原始方案不变只原样重跑 = 浪费时间。

### 3.3 输入问题不走重试

输入错了，跑 100 次也是错。区分输入问题和逻辑问题是升级链的关键分叉。

### 3.4 失败摘要必须写入状态总账

每次失败升级用户后，把失败摘要写入 `HARNESS_STATE.json` 的 `blockers` 列表，防止切换对话后遗忘。

> **一句话原则**：失败分类 → 定向调整 → 限制重试 → 及时升级。卡住不可怕，反复在原地卡住不升级才可怕。
