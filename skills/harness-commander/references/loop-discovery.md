# 循环工程详解（Loop Engineering）

**核心问题**：哪些重复出现的工作值得固化为一个可复用 Loop？用什么载体实现成本最低？

## 一、Loop Discovery — 10 问决策门

逐问应答，满足 **≥7 个 YES** 才进入 Loop 编排；否则标记 Skip。

### 决策门问答

| # | 问题 | 判定标准 | 最低证据要求 |
|---|---|---|---|
| 1 | 该意图在历史中**重复出现** ≥2 次？ | 至少 2 个独立 Task Episode，按目标+输入形状+验收边界聚类确认 | 人工记忆/会话记录 |
| 2 | 现有 Skill/规则/脚本是否**已覆盖**该意图？ | 先搜索已有资产。已有 Skill 被显式使用 = 已覆盖，不新建 | Present（文件存在） |
| 3 | 输入/前置条件是否**可稳定获取**？ | 非每次人工口述提供；可从文件系统、API、git log、CI 等稳定来源自动获取 | Wired（有获取路径） |
| 4 | 处理流程是否**可复现**（非 ad-hoc）？ | 步骤顺序可固定，不需要每次临场决策分支 | Wired（步骤链可写出） |
| 5 | 是否有**客观验证方式**？ | 自动化测试/断言/退出码/日志模式匹配可判定成功失败 | Exercised（验证方式跑过） |
| 6 | 是否有明确的**停止条件**？ | 成功/失败/证据不足/人工决策——每种情况的退出路径定义清楚 | N/A（需明确写出） |
| 7 | 若存在不可逆动作，**安全边界**具体是什么？ | 无不可逆→YES；有不可逆→需列出 blast radius + 回滚方案 + 人工确认点 | Wired（安全方案有配置路径） |
| 8 | 输入/输出/中间状态是否有**明确契约**？ | schema/类型/格式/成功码/失败码有定义，不是"看情况" | Wired（契约文件/注释存在） |
| 9 | Loop 执行过程是否**可观测**？ | 日志/trace/进度可查询；静默失败不可接受 | Exercised（日志输出已验证） |
| 10 | 有合适的**评估指标**判断每次执行质量？ | 有指标定义（成功次数、耗时 P95、误报率等），且已采集到至少一个样本 | Wired（指标采集路径存在） |

### 决策输出格式

```
Loop Discovery Result:
  Score: X/10 (threshold: 7)
  通过问: [#1, #3, #4, #5, #6, #8, #10]
  未通过问: [#2, #7, #9] — [具体阻塞原因]
  决策: [Proceed / Skip]
  建议载体: [Skill / Automation / Script / ...]
```

## 二、Owner Route — 载体选择

按成本递增，**选最小够用载体**。禁止什么都做成 Custom Agent。

| 优先级 | 载体 | 适用场景 | 决策条件 |
|---|---|---|---|
| 1 | **Covered** | 已有 Skill/规则/脚本覆盖 | 第 2 问 = YES |
| 2 | **Skill** | 需可复用的声明式能力封装，轻量 | 步骤可声明式描述，无需重型计算 |
| 3 | **Automation** | 可自动触发（定时/事件）的检查规则 | 输入来源稳定（第 3 问 YES）且触发条件清晰 |
| 4 | **Hook-Rule** | 特定事件触发（git hook / CI 门禁） | 事件明确、触发机制已有 infrastructure |
| 5 | **Script** | 确定性 Bash/Python 计算任务 | 输入输出全是文本/文件，无 LLM 判断需要 |
| 6 | **Command** | 自定义 CLI 命令，需频繁手动调用 | 频率高+需参数化，但无需自动化触发 |
| 7 | **Custom Agent** | 需独立上下文/记忆的专用子 Agent | 流程复杂到需多轮推理，现有 Agent 无法复用 |
| 8 | **Skip** | 不足 7 个 YES | 返回"Needs more evidence"，保留候选记录，日后有新证据时重评估 |

### 载体选择反模式

- ❌ 一个简单 lint + 3 行修复做成 Custom Agent
- ❌ 每天一次手工检查做成 Automation（频率太低，不值得）→ 选 Script
- ❌ 明明已有 Skill 覆盖了 80% 功能却新建一个→ 选 Covered，建议扩展现有 Skill
- ❌ 把 ad-hoc 一次性任务写成 Skill → 选 Skip 或 Script

## 三、五种运行模式

| 模式 | 触发方式 | 典型场景 | 停止条件 |
|---|---|---|---|
| **定时巡检** (Scheduled Audit) | 固定频率 cron/定时任务 | 每日代码规范审查、依赖过期检查、系统健康检测 | 本次巡检完成即停止，下次定时再触发 |
| **事件响应** (Event-Driven) | 特定事件（git push / issue 创建 / PR merge） | 提交后代码审查、部署后冒烟测试、新 issue 自动分类 | 事件处理完毕，产物已写入指定位置 |
| **目标完成** (Goal-Completion) | 明确目标推进直到达成 | 自动化迁移：逐个文件重构直到全仓库改造完成 | 目标条件达成或发现阻塞（blocker）需人工介入 |
| **主动发现** (Active Discovery) | 无外部触发，主动扫描 | 仓库内隐藏的循环工作流发现、未使用依赖扫描 | 扫描覆盖全部范围后停止，输出候选清单 |
| **系统改进** (Self-Improving) | 自身流程的优化需求 | 对已有 Loop 的误报率分析、证据等级校准、载体升级 | 改进方案已实施并验证，或新证据推翻改进假设 |

## 四、误报防火墙

以下信号**不构成**重复工作流证据，必须穿透：

| 假信号 | 为什么不可信 |
|---|---|
| 同关键词出现频次高 | `deploy` 可能指 5 个不同部署流程。聚类必须基于语义（目标+输入形状+验收边界），非关键词匹配 |
| 重复的 commit/publish/review | 只是薄薄的交付尾巴，不能证明前置的开发/测试工作流存在 |
| 已有 Skill 被显式调用 | 这是 coverage evidence，说明该需求已被覆盖处理；**不是**"应新建 Skill"的信号 |
| 单次复杂任务的步骤记录 | 一次性的复杂拆解不等于"可复现工作流"，至少需要 ≥2 个独立 Task Episode |
| 配置文件存在 | 有 `.eslintrc.js` 不代表 lint 是团队工作流的一部分（可能从未跑过） |

> **防火墙操作**：检测到任何一个假信号 → 标记该候选簇为 invalid → 不会进入 Loop Discovery 决策门。

## 五、循环收敛控制联动

Loop Discovery 只评估"该不该固化"，不负责运行时质量。固化后的 Loop 运行时监控由循环收敛控制（`loop-control.md`）接管：

| 阶段 | 负责机制 | 说明 |
|---|---|---|
| 判断是否值得固化 | Loop Discovery（本章） | 10 问决策门 |
| 编写固化规格 | Loop Spec Card | WHEN→SEE→DO→CHECK→STOP→LEAVE |
| 运行时防死循环 | 循环收敛控制 | 循环预算 3 轮 + 收敛检查 + 死循环判定 |
| 死循环诊断沉淀 | 循环收敛控制 → Loop Discovery | 死循环分析结果回灌到决策门，升级阈值或载体 |

### 死循环后的回灌规则

任何 Loop 在运行中触发死循环判定后：
1. Loop Discovery 对该 Loop 重新评分（原评分中的 4/6/7/8/10 问可能不再满足）
2. 如重新评分 < 7 → 降级载体（如从 Automation 降为 Script）或标记为 Needs Revision
3. 死循环根因写入该 Loop 的 Spec Card 的 LEAVE 部分，作为下次运行的 SEE（前置检查点）

## 六、首次评估后的跟进策略

- **Skip** → 记录评估结果 + 未通过问的阻塞原因 → 等待累积 ≥2 个新 Task Episode 之后重新评估
- **Proceed（Covered）** → 确认覆盖程度，如有缺口则记录为扩展建议（不强制）
- **Proceed（新建 Skill/Script 等）** → 编写 Loop Spec Card → 实现 → 首次运行 → 观察 ≥2 次后判定是否升级载体
- **Loop 运行中触发死循环** → 按第五节回灌规则处理
