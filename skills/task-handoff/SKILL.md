# 任务交接（Task Handoff）

生成一份「新对话也能直接接手」的结构化交接文档，避免任务换对话/换Agent后丢失上下文。

## 核心价值

任务交接的本质是：**让下一个Agent不依赖旧对话历史，只看这一份文档就能继续干活。** 写好交接文档 = 把"我知道的"变成"它也能知道的"。

## 工作流程

### 第一步：确认交接场景

先向用户确认（如用户已说明则跳过）：
1. **交接对象**：给哪个对话/哪个Agent？（如：主对话→子Agent、新对话恢复）
2. **任务状态**：进行到哪一步了？卡在什么位置？
3. **用户要求**：对方接手后要做什么？（继续开发/执行/汇报/存档）

### 第二步：收集交接信息

按以下维度向用户确认或从当前对话上下文提取：
- 项目/任务名称与目录位置
- 当前进度（已完成/进行中/阻塞）
- 本次增量（相对上次交接：新增/修改/结论，多次交接时重点收集）
- 关键文件路径（代码、文档、配置）
- 关键决策与原因（为什么这么做）
- 已知问题与踩过的坑
- 下一步计划（接手后先做什么）
- 约束与偏好（用户特别要求遵守的）

### 第三步：生成交接文档

按下方「交接文档模板」生成 Markdown 文件，保存到用户指定位置（或项目根目录，命名 `HANDOFF_日期.md` 或 `交接_任务名_日期.md`）。

**写之前先看参考示例**：`references/example.md` 有一份实战验证过的完整交接文档示例（技术分析大师项目），展示了每部分"写成什么样算好"。先读示例理解风格，再按模板为当前任务生成。

## 交接文档模板

```markdown
# {任务/项目名称}：新对话交接文档

更新时间：{YYYY-MM-DD}
用途：下一次打开新对话/切换Agent时，先阅读本文件，再继续执行。本文记录当前真实状态、已完成工作、已知问题、执行方式和后续计划，避免重新翻阅旧对话。

## 1. 任务身份与目录
- 任务/项目名称：{名称}
- 负责人/执行者：{谁在做}
- 核心目录：{路径列表}
- 关键文件：{文件路径 + 一句话说明}

## 2. 初始目标与原始需求
- 一开始想做的是什么：{一句话说清任务的起点/初心}
- 用户原始需求（如可回溯）：{转述当时的原始诉求，避免"为什么做这个"丢失}
- 参考模板/样例：{引用了哪个模板、哪个优秀案例，路径或链接}

## 3. 工具栈与环境
- 核心工具：{如 ffmpeg、Python、CodeX CLI、Obsidian、B站客户端等}
- 工具安装位置：{路径；标注是否持久化（沙箱重置后是否丢失）}
- 环境变量/配置：{配置文件位置；密钥只写存放位置不写明文}
- 依赖关系：{哪个工具/服务依赖哪个，缺失会导致什么}

## 4. 数据与数据库
- 数据库/数据源：{类型 + 位置 + 连接方式}
- 核心表/核心数据：{关键表、关键字段、数据量级}
- 数据重点：{哪部分数据最重要、最容易出错}
- 备份状态：{是否已备份、备份位置}

## 5. 当前进度
- 已完成：
  - [ ] {事项1：完成内容 + 证据/产物位置}
  - [ ] {事项2}
- 进行中：
  - {事项：卡在哪一步 / 为什么没完成}
- 阻塞/风险：
  - {事项：阻塞原因 + 恢复条件}

## 5.5 本次增量（Increment）⭐多次交接时重点写
简短的更新日志，记录"从上一次交接到现在做了什么"。AI能看懂即可，不用展开。
```
本次增量（上次交接后）：
- 新增：{新功能/新文件/新决策}
- 修改：{相对上次的变化}
- 结论：{验证结果/完成产物}
- 流程：{上次状态} → {本次动作} → {当前状态}
```
首次交接无上次记录时，此节写"首次交接，无增量"。

## 6. 关键决策与原因
- {决策1}：{原因}（{日期}）
- {决策2}：{原因}（{日期}）

## 7. 已知问题与坑
- {问题1}：{现象 + 根因 + 解决方案/绕过方式}
- {问题2}

## 8. 下一步计划（接手后先做什么）
1. {第一步：具体动作}
2. {第二步}
3. {验收标准：怎样算完成}

## 9. 约束与偏好
- {用户特别要求：如"保持纯提示词不加代码"、"不要删除XX文件"}

## 10. 关键上下文速查
- 账号/ID/密钥位置：{指向SECRET或配置位置，不直接写密钥}
- 常用命令：{命令}
- 参考文档：{链接/路径}
```

## 写作原则

1. **真实优先**：只写确实做过的事和确实存在的路径，不编造进度。写不清的标注"待确认"。
2. **路径要全**：文件路径写绝对路径或完整相对路径，不要让下一个Agent猜。
3. **决策带原因**：只写"选了A"不够，要写"为什么选A不选B"，否则对方可能推翻重来。
4. **坑要写解法**：每个已知问题必须带"怎么解决/绕过"，只列问题不给解法等于没写。
5. **接手者视角**：写完站在"第一次看这份文档的人"角度检查——TA能直接开始干活吗？
6. **敏感信息不外泄**：密钥/Token只写存放位置（如"见 SECRET.md"），不写明文。涉及隐私信息注意脱敏。
7. **工具必须写位置**：工具"用什么"和"装在哪"同等重要。只说"用了ffmpeg"对方可能找不到；要写"ffmpeg在 C:\...\bin\，已加入PATH"。标注是否持久化（沙箱环境重置后是否需要重装）。
8. **数据库写重点**：不只写"用的SQLite"，要写"核心表是cards，关键字段是timestamp/video_id，数据在 /app/data/.../dance.db"——接手的人最怕不知道数据在哪、哪张表是核心。
9. **原始需求不能丢**：交接越久，越容易只看到"当前卡点"而忘了"为什么做这个"。初始目标/原始需求永远放前面，防止接手者跑偏方向。
10. **先读示例再动笔**：生成交接文档前必须先读 `references/example.md`，理解"好的交接文档"长什么样。示例来自真实项目实战，比抽象原则更有指导性——照着它的写法填充当前任务内容。
11. **增量优先（多次交接）**：有上次交接记录时先读旧文档，重点写"这次新增/改了什么"（changelog 式，AI能看懂即可）。接手者看增量比看全量高效，能快速定位这轮实质进展。

## 边界情况

- **用户只说要交接没给任务名**：先问一句任务是什么，再生成文档
- **任务还没开始就要交接**：直接写"尚未开始"+背景信息+计划，同样有价值
- **多个子任务并行**：每个子任务独立一段，标注当前各子任务状态
- **交接给非技术Agent**：减少代码细节，突出目标和约束，路径保留
