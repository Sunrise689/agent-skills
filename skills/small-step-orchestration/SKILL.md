# 小步编排与边界委派

## 何时使用
- 触发词：批量修问题、拆任务给子智能体/子会话、并行开发、改动面失控、返工频繁、一次改太多。
- 适用：一个产品/仓库内有一批可分组的问题，需要多会话或多智能体并行推进。
- 不适用：单点小 bug（直接修完）；需要先做架构决策的大改（先补设计再编排）。
- 前置条件：主会话能看到全局问题清单；子任务执行者具备独立读改文件与自检的能力。

## 任务目标
用“小步快跑 + 边界清晰”把一批问题稳定清完：每一步改动可控、可验证、可回滚，并行任务互不踩脚，主会话始终握有产品上下文与集成权。

## 操作步骤
1. **分组**：把问题清单按“相互关联”聚成组，一个小步只处理 3~5 个关联问题；超过就再拆，宁多步不大步。
2. **明确验收**：开工前先写下本步“什么叫修好了”——可观察的行为/输出，而不是“改了哪些文件”。
3. **找根因与影响范围**：先定位根因，再列出会波及的文件与调用方；根因不明就先收敛到“能稳定复现的最小因子”，不猜着改。
4. **最小修复与自检**：只改根因所需的最小范围；改完立刻对照本步验收条件自检，通过才进入下一步。
5. **边界委派并行任务**：派发时必须给全四件套——
   - 不重叠文件：每个任务独占自己的文件集；
   - API 契约：跨任务调用的接口签名与语义提前冻结；
   - 允许/禁止范围：明确写“只许改 X，禁止动 Y”；
   - 验收条件：子任务可独立验证。
6. **主会话保留集成权**：产品上下文、跨任务组装、最终合入只由主会话做；子任务只交付改动与证据，不自行集成。
7. **每步留痕**：记录问题 ID、改动文件、证据（日志/截图/测试输出）、遗留的待集中调试项。
8. **检查面纪律**：默认只检查本步范围；只有用户明确说“集中验收 / 全局 Debug / 全局优化”才扩大检查面。

## 坑与红线
- 一小步塞超过 5 个问题、或把不相关问题混进同一步，是返工的最大来源。
- 并行任务没有文件边界 = 必然冲突；宁可串行，也不要让两个任务共享文件。
- 子任务“顺手”扩大改动范围必须拒收，退回按允许范围重做。
- 没有“明确验收”就开工等于没有完成定义，禁止跳过第 2 步。
- 每步证据必须落在文字里（问题 ID + 改动文件 + 证据），口头“修好了”不算数。

## 验证方式
- 每步对照验收条件逐条打勾，留痕记录齐全（问题 ID、文件、证据、遗留项）。
- 并行任务合入后做一次集成自检：契约对齐 + 全量构建/测试。
- 回看留痕：每个问题都能追到改动文件与证据，遗留项都进入下一步或集中调试清单。
