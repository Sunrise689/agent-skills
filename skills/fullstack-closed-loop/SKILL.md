# 全栈产品闭环交付

## 何时使用

- 触发词：多端交付、网站+小程序、后端+云端、闭环验收、灰度发布、上线、项目沉淀。
- 适用范围（先读）：只限软件产品——网站、小程序这类"一个事实、多个入口"的形态。不涉及硬件、嵌入式或任何需要物理生产的交付。
- 前置条件：产品目标已能写成一句话；代码与配置在版本库中；云端账号与环境由用户持有并提供。

## 任务目标

让同一份业务事实在多个入口一致呈现；交付过程每一级都有证据；发布可回滚；沉淀下来的都是可复用事实而非口号。

## 操作步骤

1. 定边界与命名。把产品目标写成"用户能看到什么、系统不承诺什么"（例如：学习工具不是投资建议，科普站不是诊断结论）。把项目的历史别名、阶段名统一登记为同一项目的不同叫法——多智能体协作时最常见的事故，就是把别名当成多个项目重复建设。
2. 建单一事实层。先稳定数据与规则，再做页面：数据归一化 → 按维度重采样/加工 → 识别或计算引擎产出候选 → 证据、门控与冲突裁决 → 输出统一的 JSON 事实。前端只消费事实层的结构化字段（标识、状态、数值/几何、确认标志），不允许前端自行推断结论或重写算法。
3. 多入口各管交互。网站、小程序各自只负责自己的交互形态（展示、开关、表单、缓存），共享后端事实与版本字段，页面之间不复制算法。没有云服务时允许明确的 demo/fallback，但必须标注数据来源，不得把演示数据冒充真实数据。
4. 后端按能力拆分。服务按能力域组织路由（分析、查询、报告、文件等），每个入口使用稳定路径与可读错误；报告/文案类生成模块只能组织语言，不能改写分析引擎产出的事实。
5. 云端接入先只读核验。记录环境 ID、服务名、端口、健康路径、前端传输方式与密钥变量名——不记录密钥值。先跑只读验证脚本确认 `/health`、根路径、接口文档和一条真实业务查询，再决定部署；部署源固定为项目根目录，禁止上传历史快照目录。
6. 验收走证据阶梯。依次通过并逐级记录（路径、时间、结果、未完成项）：静态检查（JSON/模板/样式/脚本）→ 单元与端到端离线测试 → 开发者工具编译 → 本地接口与真实数据烟测 → 部署包路径/编码/密钥扫描 → 云端新版本健康与接口检查 → 灰度 → 真机预览 → 上传/提审。任一级未通过，产物保留为"候选"状态，不得宣称完成。
7. 灰度发布留回路。新版本先 0% 流量探活，再小比例灰度；至少确认健康检查、全部业务路由、关键字段、错误信息脱敏和小程序侧调用可达。异常时把流量切回保留的旧版本；禁止在生产容器或线上环境直接改文件。
8. 项目记忆只写"可复用事实"。沉淀分三组：真实产物路径（可打开的目录/仓库/接口）、验收证据（测试输出、截图、健康检查结果）、仍未完成的外部动作（待提审、待办权限、待用户确认项）。把"文档/方案里说可以"与"代码/接口/真机已经证明"严格分开，后续交接、迭代、汇报都从这三组事实生成。

## 坑与红线

- 多智能体协作中命名不统一会导致重复建设同一产品；开工前先登记别名清单。
- 前端绝不复制后端算法；发现两处相似逻辑时，回收到事实层或后端能力域。
- 验收阶梯不得跳级：未过离线测试不进真机，未过灰度不全量。
- 密钥只记变量名不记值；部署包扫描必须包含密钥与个人路径检查。
- 线上问题靠回滚解决，不靠热改生产文件。
- 沉淀里禁止把未验证的计划写成已完成。

## 验证方式

- 事实一致性：同一查询在网站与小程序（或任两个入口）返回一致的关键字段与版本号。
- 证据链：每一级验收都有记录（路径/时间/结果），可回溯到具体文件与命令输出。
- 发布回路：灰度期间做一次回滚演练或人工检查回滚开关，确认能在可接受时间内切回旧版本。
- 沉淀质量：项目记忆中每条事实都能落到真实路径或证据文件。
