# 按任务比例验证

## 何时使用

**触发词**："按任务比例验证""最小验证""最小修改""不要扩大范围""只改这一点""小改动小验证"。

**适用**：
- 边界明确的单点修改：改一个函数、调一个配置项、修一处明显笔误
- 用户明确说"只做 X，别动别的"的任务
- 风险面小的脚本、文档、样式类调整

**不适用**：
- 需求本身模糊、验收标准未定义的任务——先澄清再执行，而不是用扩大验证来兜底
- 涉及删除数据、支付、权限、生产环境等高风险修改——验证须足额，不适用"最小"
- 用户明确要求全面回归或深度排查的场景

**前置条件**：能从任务描述还原出"改哪里、改成什么样、怎么算完成"三点；还原不出来即视为非简单任务，先向用户澄清边界。

## 任务目标

让验证强度与任务规模成正比：小任务不背大流程的包袱，大任务不因图省事而漏验。核心纪律——**只做完成结果所需的最小修改和最小验证，保留用户明确要求的备份与必要安全检查**；不因通用工程习惯自动扩展成全局 Debug、全量回归或流式测试；只有任务自身风险或用户明确要求时才扩大范围。

## 操作步骤

1. **判界**：用一句话复述任务，写出本次"改动边界清单"（要改的文件/函数/配置 + 不许动的范围）。边界不清晰即按非简单任务处理，先澄清。
2. **定级**：对照下表确定验证强度，明确声明本次执行的规模档位。
3. **最小修改**：只改边界清单内的内容。顺手看到的其他问题——记录下来单独汇报，不夹带修改。
4. **最小验证**：只验证本次改动直接影响的路径；需要备份时只备份被改动的对象；涉及删除或覆盖时保留必要防护（如先复制再改）。
5. **收尾汇报**：报告"改了什么、验证了什么、没验证什么、为什么无需验证"；边界外发现的问题以清单形式交还用户决定是否处理。

**任务规模 → 验证强度对照表**

| 任务规模 | 典型例子 | 修改纪律 | 验证强度 |
|---|---|---|---|
| 微（一行级） | 改错别字、调数值、换文案 | 单点直改 | 目视确认，或跑一次最小复现 |
| 小（单文件） | 改一个函数、加一个开关 | 只动该文件，不重构 | 针对性跑相关用例，或手动过一遍主路径 |
| 中（跨文件） | 一个小功能的完整闭环 | 先列改动面清单，逐项对齐 | 覆盖改动面的定向测试 + 关键交互自测 |
| 大（系统性） | 架构调整、批量迁移 | 须有用户确认的方案 | 全量回归/分阶段验证——只有此档允许"升级" |

## 坑与红线

- **红线**：不得以"工程习惯"为由给简单任务自动附加全局扫描、全量回归、流式测试或大规模重构。
- **红线**：最小验证不等于零验证——任何改动都要有至少一份直接证据（运行输出、截图、用例结果）证明目标达成。
- **坑**："顺手优化"是最常见的越界来源；发现即记录上报，不执行。
- **坑**：扩大范围的合法理由只有两个——任务自身风险（触碰共享数据/生产环境等），或用户明确要求。自查是否混入了第三个理由。
- **坑**：把"没验证"写成"验证过了"。汇报必须区分"已验证 / 未验证 / 无需验证"三种状态。

## 验证方式

- 回看改动 diff：所有改动均在边界清单内，无夹带修改。
- 回看验证记录：存在与任务规模档位匹配的最小验证证据。
- 自查提问：本次是否做了任何"任务没要求、风险也没要求"的多余动作？有则说明越界，返工收敛。
