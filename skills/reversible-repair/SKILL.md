# 可回滚的 UI/状态修复

## 何时使用

- 触发词：界面点不动、消息提交失败、会话切换异常、配置不生效、状态错乱、修复要能回滚。
- 适用：本地安装的 GUI 桌面应用（聊天客户端、编辑器、桌面工具等）出现 UI 或会话状态故障，且故障大概率由本地持久化状态或配置文件引起。
- 不适用：纯代码 bug（应改源码重新构建）、无本地状态的服务端问题、需要重装才能解决的安装损坏。
- 前置条件：能操作真实桌面会话（能截图、能点击、能重启应用）。无头/沙箱环境无法完成 UI 验收，最多只能做到"部分完成"并明确标注。

## 任务目标

在不丢失用户数据（数据库、历史记录、锁文件）的前提下，用最小、可回滚的修改恢复应用的正常交互，并以用户的原始操作路径验证修复真实生效。

## 操作步骤

1. 复现并记录。亲自执行一次出问题的原始动作，记录：触发动作（点了什么、期望什么、实际什么）、应用版本、完整报错文本、日志尾部（应用日志通常在用户配置目录下）、当前会话/窗口状态截图。把"现象"与"猜测"分开写。
2. 时间戳备份。对计划触碰的每一类文件（配置、状态文件、用户配置目录）先整体复制一份，命名带时间戳（如 `config.json.bak-20260928-1530`）。数据库、历史记录、锁文件一律不碰、不删、不"顺手清理"。记录应用当时是否在运行。
3. 假设驱动的最小修改。只修改"能解释当前现象"的持久化状态或配置项：先写下因果假设（这个字段为什么导致这个现象），一次只改一处，用 diff 记下改前/改后值。优先改纯配置（JSON/INI 等），谨慎改状态文件；禁止重置整个用户目录，禁止用删除数据库的方式"重置"问题。
4. 重载实际运行进程。完全退出应用（含托盘与后台进程，用进程列表确认），再重新启动。配置"已写入磁盘"不等于生效——运行中的进程通常持有内存态。重载后先确认应用内读到的就是新值。
5. 按原动作做最小验收。重做第 1 步记录的原始动作，逐项核对：操作是否真实成功（消息真的发出、会话真的切换）、日志是否不再出现同类错误、抽查 1~2 个相邻功能确认未被波及。截图留证。
6. 收尾或回滚。验收通过：保留修改，记录"改了哪个文件哪个字段、依据、验收证据"。验收不通过：用备份原样恢复，重载进程，确认回到修复前状态，再重新形成假设；禁止在同一份未回滚的状态上继续叠加修改。

## 坑与红线

- 按钮可见不等于可用；配置写入成功不等于生效；静态自检/文件校验通过不等于运行正常。三者都不能替代真实 UI 证据。
- 缺少 UI 验收（环境不允许、无法复现原动作）时，必须把任务标记为"部分完成"并列出未验证项，不得声称已修复。
- 一次只改一处。多处同时修改后即使恢复正常也无法归因，也无法安全回滚。
- 锁文件、数据库、历史记录即使"看起来坏了"也不要删除；它们损坏往往另有原因，删除会丢数据。
- 修改前确认应用已退出（或明确该文件支持热重载），否则可能被进程回写覆盖。
- 不做与当前现象无关的"顺手优化"。

## 验证方式

- 前后对照：修复前后各执行一次同一原始动作并留证（截图/日志），结果必须从失败变为成功。
- 回滚可用：确认备份文件完整、可读、路径正确，恢复后应用能回到修复前状态。
- 稳定性：实际使用一段时间后复查日志，确认无同类错误新增。
